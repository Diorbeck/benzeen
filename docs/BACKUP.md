# Резервное копирование и восстановление БД

Ежедневный бэкап продакшн-базы PostgreSQL выполняется через GitHub Actions:
`.github/workflows/db-backup.yml`.

## Что делает workflow

- Запускается каждый день в **02:00 UTC** (≈07:00 по Ташкенту) и вручную
  (вкладка **Actions → Daily DB Backup → Run workflow**).
- Делает `pg_dump -Fc` (custom format, сжатый, поддерживает выборочное
  восстановление), затем `gzip`, затем **шифрует** результат
  `AES-256-CBC` (PBKDF2, случайная соль).
- Сохраняет **зашифрованный** дамп как приватный артефакт GitHub Actions с
  хранением **14 дней**.
- Если заданы AWS-секреты — дополнительно копирует **зашифрованный** файл в S3.

> 🔒 **Почему шифрование обязательно.** Репозиторий публичный, а дамп содержит
> персональные данные клиентов (телефоны, адреса). Workflow **аварийно
> завершается**, если секрет `BACKUP_PASSPHRASE` не задан — незашифрованный дамп
> не создаётся никогда. Строка подключения и пароль передаются через env и
> **не печатаются в лог** и не попадают в argv.

## Необходимые секреты репозитория

Settings → Secrets and variables → Actions → **New repository secret**:

| Секрет | Обязательность | Назначение |
| --- | --- | --- |
| `DATABASE_URL` | **обязательно** | Полная строка подключения к прод-базе |
| `BACKUP_PASSPHRASE` | **обязательно** | Пароль шифрования/дешифрования дампа. Храните его **отдельно** от репозитория (менеджер паролей). Без него восстановление невозможно. |
| `AWS_ACCESS_KEY_ID` | опционально | Включает выгрузку в S3 |
| `AWS_SECRET_ACCESS_KEY` | опционально | — |
| `AWS_REGION` | опционально | напр. `eu-central-1` |
| `BACKUP_S3_BUCKET` | опционально | напр. `s3://my-bucket/benzeen-backups` |

S3-выгрузка включается только если заданы `AWS_ACCESS_KEY_ID` и
`BACKUP_S3_BUCKET`.

## Как скачать бэкап

1. **Actions → Daily DB Backup** → выберите нужный запуск.
2. В разделе **Artifacts** скачайте файл `benzeen-YYYYMMDD-HHMMSS.dump.gz.enc`.

## Как расшифровать и восстановить — ТОЛЬКО НА КОПИИ

> ⚠️ **Никогда не восстанавливайте поверх боевой базы.** Сначала создайте
> отдельную (пустую) базу-копию и проверьте дамп на ней.

Понадобится значение секрета `BACKUP_PASSPHRASE`.

```bash
# 0. Экспортируйте пароль (не оставляйте его в истории shell — используйте
#    read -s, чтобы ввод не сохранялся).
read -rs BACKUP_PASSPHRASE; export BACKUP_PASSPHRASE

# 1. Расшифровать + распаковать → получаем .dump (custom format)
openssl enc -d -aes-256-cbc -pbkdf2 -pass env:BACKUP_PASSPHRASE \
  -in  benzeen-YYYYMMDD-HHMMSS.dump.gz.enc \
  | gunzip > benzeen-YYYYMMDD-HHMMSS.dump

# 2. Создать ПУСТУЮ копию (другое имя/инстанс, НЕ прод!)
createdb -h <host> -U <user> benzeen_restore_test

# 3. Восстановить в копию
pg_restore --no-owner --no-privileges \
  -h <host> -U <user> -d benzeen_restore_test \
  benzeen-YYYYMMDD-HHMMSS.dump

# 4. Проверить данные в benzeen_restore_test, и только потом —
#    при реальной аварии — повторить восстановление на проде
#    осознанно, вручную, с предварительным бэкапом текущего состояния.

# 5. Удалить расшифрованный .dump, когда закончите — он не зашифрован.
rm -f benzeen-YYYYMMDD-HHMMSS.dump
```

Проверить, что файл действительно расшифровывается (без полного восстановления):

```bash
openssl enc -d -aes-256-cbc -pbkdf2 -pass env:BACKUP_PASSPHRASE \
  -in benzeen-YYYYMMDD-HHMMSS.dump.gz.enc | gunzip | pg_restore --list | head
```

## Рекомендации

- Раз в месяц делайте «учебное восстановление» на копии — бэкап без
  проверенного восстановления не считается рабочим. Заодно проверяется, что
  `BACKUP_PASSPHRASE` у вас сохранён и рабочий.
- Храните `BACKUP_PASSPHRASE` в менеджере паролей владельца, а не только в
  GitHub Secrets: если доступ к репозиторию потерян, пароль всё ещё нужен для
  расшифровки скачанных ранее артефактов.
- Если используете managed-Postgres (Neon и т.п.), держите включёнными и их
  встроенные снапшоты — это дополнительный независимый уровень защиты.
